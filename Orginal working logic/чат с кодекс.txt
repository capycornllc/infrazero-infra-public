Сейчас там есть только:

- local all all peer
- host replication ${repl_user} ${PRIVATE_CIDR} scram-sha-256
- host all all ${PRIVATE_CIDR} scram-sha-256
А в логе/диалоге ключевой симптом именно такой:
no pg_hba.conf entry for host "127.0.0.1"
user "postgres"

no pg_hba.conf entry for replication connection

Это идеально совпадает с кодом. Patroni действительно ходит в локальный PostgreSQL по 127.0.0.1, и OVH-конфиг это не разрешает. Поэтому state: unknown, две replica без leader, Receive LSN unknown, Replay LSN unknown — не “магия Patroni”, а прямое следствие отсутствующих pg_hba правил.
Что в ответе ChatGPT верно
Нужно добавить localhost-правила в Patroni YAML, именно в postgresql.pg_hba, а не просто руками в текущий /etc/postgresql/.../pg_hba.conf, потому что Patroni управляет итоговым pg_hba.
Правильный блок для OVH должен быть примерно таким:
pg_hba:
  - local all postgres peer
  - local all all peer
  - host all postgres 127.0.0.1/32 scram-sha-256
  - host replication ${repl_user} 127.0.0.1/32 scram-sha-256
  - host replication ${repl_user} ${PRIVATE_CIDR} scram-sha-256
  - host all all ${PRIVATE_CIDR} scram-sha-256
Важно: не хардкодить replicator и 10.10.0.0/24, а использовать ${repl_user} и ${PRIVATE_CIDR}.
Что ChatGPT сказал неточно
Он пишет, что в рабочем Hetzner были явные строки 127.0.0.1/32. В текущем коде это не так:
[bootstrap/hetzner/db.sh (line 2610)](D:/Dimas/Code/Work/Infrazero/infrazero-infra-public/bootstrap/hetzner/db.sh:2610)
[bootstrap/hetzner/db-replica.sh (line 465)](D:/Dimas/Code/Work/Infrazero/infrazero-infra-public/bootstrap/hetzner/db-replica.sh:465)
Hetzner сейчас работает потому, что там стоит слишком широкое:
- host replication ${repl_user} 0.0.0.0/0 scram-sha-256
- host all all 0.0.0.0/0 scram-sha-256
То есть 127.0.0.1 покрывается случайно через 0.0.0.0/0. Это работает, но с точки зрения безопасности хуже. Правильнее привести Hetzner и OVH к одному явному шаблону: 127.0.0.1/32 + PRIVATE_CIDR, без 0.0.0.0/0.

Код сам активирует operational access после успешного deploy: [LigamentWizardApp.tsx (line 1038)](D:/Dimas/Code/Work/Infrazero/infrazero/src/UI/Ligament/Wizard/App/LigamentWizardApp.tsx:1038)

Если пользователь уже подключился локальным WireGuard с тем же ключом/IP, а backend поднимает второй туннель с тем же peer, WireGuard на сервере начинает “перекидывать” endpoint этого peer туда-сюда. Это вполне может давать client_loop: send disconnect и Connection timed out.

App / VPN / Agent
